# Audit fonctionnel — Socle transverse (dashboards, notifications, chatbot, référentiels)

**Date** : 11 juillet 2026
**Périmètre** : `backend/src/index.js`, `routes/{dashboard,health,performance,newsfeed,notifications,chat,referentiels}.js`, `services/{scheduler,job-queue,notification,push-notifications}.js`, `ai-agent/app.py`, `frontend/src/{App.jsx,components/Layout.jsx,contexts/AuthContext.jsx,services/api.js}`, pages Dashboard / DashboardExecutif / PerformanceDashboard / NewsFeed / AdminCatalogue / AdminAlertThresholds / AdminAssociations.

---

## 1. Couverture fonctionnelle réelle

Le socle transverse couvre aujourd'hui quatre familles de fonctions, toutes lisibles dans le code :

- **Dashboards** : un accueil combiné (`Dashboard.jsx` / `GET /dashboard/kpis`) avec KPI collecte/production/RH/stock/exutoires, alertes contextuelles et activité récente ; un dashboard « Performance » orienté contrôle de gestion (`PerformanceDashboard.jsx`, 5 endpoints `/performance/*` : tendance 6 mois, répartition des sorties, heatmap d'activité, scorecard objectifs, KPI industriels) ; et un **dashboard exécutif V3** (`DashboardExecutif.jsx` / `GET /dashboard/executive`) avec 8 KPI stratégiques comparés à N-1 et seuils d'alerte configurables (`AdminAlertThresholds.jsx` / `alert_thresholds`).
- **Notifications** : envoi manuel email/SMS via Brevo (`routes/notifications.js`, réservé ADMIN/RH), un scheduler CRON riche (`services/scheduler.js` — rappels RDV, fins de contrat J-30/J-15, jalons insertion, alertes maintenance, purges RGPD, sync VAK/Pennylane, veille news…) et une brique **Web Push** complète (VAPID, service worker, `NotificationBell.jsx`) réellement câblée sur les incidents de tournée (`routes/tours/*`).
- **Chatbot IA** : SolidataBot, assistant conversationnel Claude avec 5 outils lecture seule (stock, planning, collecte, heures, CAV), filtrage RGPD par rôle, historique, suggestions contextuelles, et une UX front soignée (panneau slide-in, dictée vocale, synthèse vocale FR) — bien adaptée à un public parfois éloigné du numérique.
- **Référentiels** : catalogue produits, dimensions (genre/saison/gamme), types de conteneurs, exutoires, positions — CRUD simple, écriture réservée ADMIN.
- **Socle** (`index.js`) : Helmet/CSP, CORS strict, rate limiting global + auth, Socket.IO authentifié par JWT avec adapter Redis (multi-instance), servir `/uploads` durci (whitelist MIME, anti path-traversal), health checks `/live`/`/ready`/`/` avec timeouts, auto-init DB + migrations idempotentes au démarrage.

C'est une base technique sérieuse, globalement conforme aux règles internes du projet (paramétrage SQL, `authenticate`/`authorize`, tables `IF NOT EXISTS`).

## 2. Adéquation aux besoins des parties prenantes

Pour le **terrain** (salariés en insertion, peu familiers du numérique), SolidataBot est le point fort : ton simple, emojis, vocal bidirectionnel, suggestions contextualisées par heure/rôle. Pour la **conformité réglementaire** (Refashion, Métropole, DREETS), le dashboard exécutif expose déjà les bons agrégats (taux de valorisation vs objectif 75 %, sorties positives IAE vs cible 55 %, subvention Refashion du trimestre, CO2 évité). Pour la **direction**, l'ambition est la bonne (1 page, 8 KPI, seuils configurables, N-1) — mais l'exécution bute sur un problème d'adoption détaillé en section 4 : rien dans la navigation ne mène à cette page.

Point notable et positif : le fil d'actualité (`NewsFeed.jsx`) a un deep-link propre (`/news?article=id`) avec scroll-to + surlignage, et l'auto-alimentation (veille sectorielle 21 j de rotation) évite l'écueil déjà documenté dans l'historique du projet (fil qui se tarit).

## 3. Benchmark marché

Recherches ciblées effectuées (voir sources) : en 2026, les éditeurs ERP (SAP Joule, Oracle NetSuite AI, Microsoft Copilot Studio, ChatERP) font évoluer leurs assistants de **chatbots réactifs** vers des **agents proactifs** qui se déclenchent sur événement (nouvel enregistrement, seuil franchi) et exécutent des actions multi-étapes, pas seulement des requêtes en lecture. SolidataBot reste au premier palier : 5 outils lecture seule, invoqué uniquement à la demande — cohérent avec un chantier récent (chat + tool-use), mais en retrait par rapport à la tendance « agents autonomes » qui devient un différenciateur attendu. Comparé à un éditeur du secteur (Ming Insertion, cité par les résultats de recherche), qui met en avant un « tableau de bord avec alertes et rappels d'échéance » et une transmission automatique ASP, SOLIDATA est à parité sur les alertes/jalons d'insertion mais n'a pas d'équivalent à la nouvelle plateforme obligatoire SIAE Connect (DUI, conventions DDETS) — hors périmètre strict de ce module mais à noter pour la feuille de route insertion. Sur les standards socle ERP (navigation, recherche globale, notifications multicanal, dashboards exécutifs) : SOLIDATA a la navigation à 4 niveaux et les dashboards, mais **aucune recherche globale** (pas de barre de recherche transverse dans `Sidebar.jsx`/`TopBar.jsx`) alors que l'application compte 75+ pages et un menu profond — un écart net face aux standards du marché où la recherche globale (Cmd+K / palette de commandes) est désormais quasi systématique.

Sources : [ERP AI Chatbots: Business Use Cases & Best Practice (2026)](https://www.hso.com/blog/erp-ai-chatbots/) · [AI and Copilot in ERP: What Executives Need to Know in 2026](https://www.digmatix.com/en/blogs/ai-and-copilot-erp-what-executives-need-know-2026) · [Ming Insertion - URIAE](https://www.uriaenpdc.org/accueil/nos-services/ming-insertion/)

## 4. Forces / faiblesses / manques

**Forces observées dans le code** : health checks avec timeouts et distinction `live`/`ready` (bonne pratique Kubernetes-like, rare dans ce type de projet) ; verrou distribué PostgreSQL (`pg_try_advisory_lock`) sur le scheduler, qui évite les doublons d'envoi en cas de scale-out ; cache Redis sur les KPI avec clé par tranche de minute (invalidation naturelle) ; durcissement `/uploads` (whitelist MIME + CSP sandbox) déjà en place ; SolidataBot RGPD-aware (un COLLABORATEUR ne peut interroger que son propre planning/ses propres heures, contrôle fait à la fois côté Node et côté Python) ; seuils d'alerte déjà pré-remplis avec 5 valeurs réalistes (pas d'écran vide à la première utilisation).

**Faiblesses et manques** :
- **Dashboard exécutif et page « Seuils d'alerte » orphelins de la navigation.** `DashboardExecutif.jsx` (route `/dashboard-executif`) et `AdminAlertThresholds.jsx` (route `/admin-alert-thresholds`) existent, sont fonctionnels côté API, mais **n'apparaissent nulle part dans `NAV_TREE`** (`Layout.jsx`). Le seul chemin d'accès est de connaître l'URL ou de suivre un lien texte codé en dur (`<a href>`, pas un `<Link>` React Router) placé dans le pied de page du dashboard exécutif lui-même. Le code (« V3 — audit Direction, action 11 du plan d'action ») montre que c'était un chantier volontaire et suivi ; pourtant aucune ligne de l'historique `CLAUDE.md` (section 12) n'en fait mention. Tout indique une fonctionnalité livrée mais jamais « branchée » côté produit — la direction risque de ne jamais savoir qu'elle existe.
- **Incohérence de contrôle d'accès sur `dashboard.js`.** Le routeur applique `authenticate` mais **aucun `authorize()`** sur `/kpis`, `/objectifs` ni `/executive` — au contraire de `performance.js`, qui restreint explicitement par rôle selon le chemin. N'importe quel rôle authentifié (y compris COLLABORATEUR ou RESP_BTQ) peut donc appeler directement `GET /api/dashboard/executive` et obtenir les KPI stratégiques (trésorerie, subvention Refashion, CO2, sorties insertion) réservés à ADMIN/MANAGER côté frontend, ainsi que les mouvements de stock, factures impayées et changements de statut candidats renvoyés par `/kpis`. Ce n'est pas une fuite vers l'extérieur (JWT valide requis), mais cela contredit la règle même du projet (« Toute route sensible doit utiliser `authenticate` + `authorize` », CLAUDE.md §8).
- **Deux implémentations parallèles de SolidataBot.** `backend/src/routes/chat.js` (Node, réellement monté dans `index.js`, appelé par `SolidataBot.jsx`) et `ai-agent/app.py` (Flask, tools quasi identiques) coexistent. `ai-agent` n'apparaît dans **aucun** `docker-compose*.yml` à la racine, dans **aucune** configuration nginx, et n'est appelé par **aucun** composant frontend — il est mort en production — mais reçoit encore des correctifs de sécurité (derniers commits sur `ai-agent/`) et reste documenté dans `CLAUDE.md` comme si actif, avec sa propre suite de 13 tests pytest. Signe que la dérive a déjà commencé : `ai-agent/app.py` interroge la table `matieres` (`categorie`/`sous_categorie`) alors que `chat.js` interroge `categories_sortantes` (`nom`/`famille`) — un schéma que l'agent Python ne verrait probablement plus correctement s'il était un jour redéployé tel quel.
- **Modèle Claude par défaut déprécié encore présent à 3 endroits.** `chat.js`, `services/predictive-ai.js` et `routes/vehicles.js` utilisent encore `process.env.CLAUDE_MODEL || 'claude-sonnet-4-20250514'`, alors que ce même défaut a **déjà causé deux incidents de production documentés** dans l'historique du projet (versions 2.3.0 et 2.4.3, sur `insertion-ai.js`, corrigés en basculant vers `'claude-sonnet-5'`). En configuration Docker actuelle (`docker-compose.prod.yml` fixe `CLAUDE_MODEL=claude-sonnet-5` par défaut), le risque est dormant — mais toute exécution hors ce compose précis (autre `.env`, redéploiement partiel) réintroduit exactement le mode de panne déjà vécu (« Erreur analyse IA » opaque).
- **Notifications push à couverture partielle.** Le web push est réellement déclenché pour les incidents et re-optimisations de tournée (`routes/tours/*`), mais **aucun** des jobs du scheduler (rappels RDV J-1, fins de contrat J-30/15, alertes jalons insertion, maintenance véhicule) n'envoie de push — ils restent Brevo email/SMS uniquement. Un utilisateur qui « active » les notifications push via la cloche (`NotificationBell.jsx`) peut donc légitimement croire qu'il recevra ces rappels alors qu'il ne recevra que les alertes temps réel de collecte.
- **Absence de recherche globale**, alors que la navigation atteint 4 niveaux de profondeur sur 75+ pages (`Sidebar.jsx`/`TopBar.jsx` n'exposent aucun champ de recherche transverse) — un écart net avec les standards ERP actuels.
- **Irritants mineurs** : `AdminCatalogue.jsx` n'utilise pas les composants de design system communs (`PageHeader`, `Section`, classes `card-modern`) contrairement au reste du périmètre audité — rendu visuellement disparate ; `NewsFeed.jsx` retombe sur `alert()`/`confirm()` natifs du navigateur pour les erreurs de création/suppression, alors qu'un composant `useToast()` existe et est utilisé ailleurs (`AdminAlertThresholds.jsx`) ; les suggestions de secours du chatbot (`FALLBACK_SUGGESTIONS`, utilisées seulement si `/chat/suggestions` échoue) proposent des questions (« Pourquoi la marge a augmenté ? ») qu'aucun des 5 outils réels ne peut satisfaire.

## 5. Recommandations priorisées

| Priorité | Recommandation | Effort |
|---|---|---|
| P1 | Ajouter les entrées de navigation manquantes pour `/dashboard-executif` et `/admin-alert-thresholds` (section Analyse/Administration) | S |
| P1 | Ajouter `authorize('ADMIN','MANAGER')` (ou équivalent différencié) sur `dashboard.js`, en particulier `/executive`, pour aligner le contrôle d'accès backend sur ce que montre déjà le frontend | S |
| P1 | Remplacer le défaut `claude-sonnet-4-20250514` par `claude-sonnet-5` dans `chat.js`, `predictive-ai.js`, `routes/vehicles.js` (cohérence avec `insertion-ai.js`) | S |
| P1 | Statuer explicitement sur `ai-agent/` : le documenter comme déprécié dans `CLAUDE.md` (ou le décommissionner) pour stopper la maintenance et la confusion sur la source de vérité du chatbot | M |
| P2 | Étendre le déclenchement push aux jobs planifiés à fort enjeu métier (fin de contrat, jalon insertion en retard, alerte maintenance) en plus des incidents tournée | M |
| P2 | Introduire une recherche globale transverse (candidats, employés, CAV, tournées) accessible depuis la TopBar | M |
| P2 | Harmoniser `AdminCatalogue.jsx` sur le design system commun (`PageHeader`/`Section`/`card-modern`) et remplacer les `alert()`/`confirm()` natifs de `NewsFeed.jsx` par `useToast`/`useConfirm` | S |
| P2 | Faire évoluer SolidataBot d'un chatbot réactif vers quelques déclenchements proactifs simples (ex. message spontané si CAV plein détecté), pour suivre la tendance marché « agent » plutôt que « chatbot » | L |

**Score global du module : 7/10.** Base technique solide et cohérente avec les règles internes du projet (sécurité socle, scheduler robuste, chatbot RGPD-aware), aucun blocage métier identifié — mais l'adoption réelle de deux fonctionnalités à forte valeur (dashboard exécutif, seuils d'alerte) est compromise par un oubli de branchement navigation, et la gouvernance de l'IA (deux chatbots, modèle déprécié résiduel) mérite d'être clarifiée avant d'ajouter de nouvelles briques IA.
